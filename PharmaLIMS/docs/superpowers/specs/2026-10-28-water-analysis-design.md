# Trusted Water analysis — design

## Evidence and intent

Actual site reference `9C2AA5FD` is SQL229 UPDATE denied on dbo.Samples under native AMEEN\LimsUatAdmin, application admin. Trusted Water registration was staged successfully, but analysis still executes legacy direct DML. Fix the six analysis operations as one coherent boundary; standard desktop principals retain their existing read-only SQL rights.

Installed source bundle: 20 files, normalized copies and raw hashes in `/workspace/.cloud-setup/water-analysis/site-source/metadata.json`. Installed ResultsEntry Part3/5/6 and Water helper policies contain additional safeguards absent from repository HEAD. Preserve these exactly when merging the trusted adapter; never replace the local family with the base variant. Water/EM/PRM local work, all historical rows/signatures/audits, TLS/SID enforcement, Production configuration and unmerged PR62 remain protected.

## Scope and approaches

Implement StartAnalysis, SaveResults, SubmitReview, Review, Approve and CorrectTimes. Existing user direction is to repair the analysis cycle through approval using the established trusted-service pattern. Broad client DML grants violate the user's constraints. A Start-only patch leaves the identical failure in save/review/approve and is incomplete. The implementation choice is typed requests, independent service-side validation under retained SQL locks, and a narrow owner-executing procedure performing atomic writes. Never accept SQL text, table names, client roles/pass-fail/specification metadata, or client-selected server output plans over the pipe.

Certificate issue/print/cancel and manual investigation editing are separate existing mutating boundaries. They are not made qualified by these six operations; the UI must report deployment availability honestly and no laboratory-readiness claim is permitted until those phases receive native/site evidence.

## Architecture and interfaces

* Trusted library adds `WaterWorkflowRequest` (TargetServer, TargetDatabase, Operation, SampleId, SampleNumber, ExpectedStatus, ExpectedSnapshot, AnalysisStartedAt?, Times?, Results[]), `WaterWorkflowRow` for raw result/remarks/equipment/resource/LES inputs, `WaterWorkflowTimes` for five editable times, and `WaterWorkflowResult` (RequestId, State, SampleId, SampleNumber, Status, SignatureId, CompletedTests, PendingTests, QualityEventSummary).
* Allowed operations exactly `StartAnalysis`, `SaveResults`, `SubmitReview`, `Review`, `Approve`, `CorrectTimes`. Transport actions `WaterWorkflow`, `WaterWorkflowResolve`, `WaterWorkflowCancel`. Original Operation participates in immutable receipt identity even on resolve/cancel. JSON uses PascalCase and rejects unknown fields. Request IDs, canonical request hashes, SID and actor bind receipts. Existing 32768-character payload /65536-byte frame limits reject oversized input without truncation.
* Client and host use the same `Services.WaterWorkflowSnapshot.Load(SqlConnection,SqlTransaction,int)` read-only query set and deterministic binary fingerprint. Snapshot contains full sample header; authoritative result/spec/rowversion/attribution; current equipment/history identities; latest resource and LES evidence. Database clock is returned separately, never hashed. Client takes before/after snapshots around load to prevent binding an old visible grid to newer stored data. Host takes retained UPDLOCK/HOLDLOCK snapshots inside Serializable transaction and compares the original expected hash before any write.
* Host validates target fields against its private connection. Product deployment is UAT-only behind independent `EnableWaterAnalysisUat=false` default; no Production activation. UAT catalog must use established EQ001_UAT_ / PharmaLIMS_EQ001_UAT_ isolation prefixes, encrypted certificate-validated SQL, Windows-integrated service connection. Actual staging pins exact AMEEN/UAT database; CI adapts only the explicit disposable SQL target guards, preserving real Windows origin and readonly client identities. Client may use the existing account-bound DPAPI readonly SQL connection in native CI; target server/catalog must still exactly match host.
* `Services.WaterWorkflowValidator` builds a server-only `WaterWorkflowMutationPlan` from locked SQL data and raw typed input. Scientific values/spec/identities, readiness, role independence, chronology, incubation, pending-only investigation completion, OOS/QE and exact precision are independently checked. Plan objects are not remote API inputs.
* `dbo.EQ001_UAT_WaterWorkflow` accepts Mode(Read/Resolve/Cancel/Commit), Operation, RequestId, SampleId, expected state, canonical request hash/body, actor/version/SID/signature reason+meaning, server-only Plan JSON. Requires explicit transaction, exact isolated SQL target, and independent Windows signing principal; refuses sysadmin origin. New receipt table is append-only. Only service receives EXECUTE on this procedure; existing client and service direct-DML rights remain unchanged.
* All sample/test/equipment/resource/LES/signature/audit/OOS/plan writes, post-trigger exact numeric verification and receipt commit form one transaction. Approval synchronizes linked Water plan inside that transaction, replacing the current post-commit client DML.
* `TrustedWaterWorkflowStore` consumes one existing fresh native-SID/application-user/auth-version ticket; roles are revalidated in SQL/host. Existing generic login/signature behavior remains intact. No workflow request can choose a different role or mutation plan. Resolve/cancel retain original request identity; a committed result returns its historical outcome, never executes twice. Cancelling an uncommitted ID inserts a permanent tombstone without changing clinical rows.
* `ResultsEntry.TrustedWaterWorkflow.cs` captures immutable input before signature, uses the existing fresh signature dialog, persists DPAPI recovery before dispatch, invokes service, then reloads persisted state. Existing legacy branch remains only when trusted transport is disabled; trusted failures never fall back to local DML. Six handlers dispatch before legacy DDL/DML. UI labels must not claim certificate issuance is qualified.

## Scientific invariants

Preserve installed exact raw numeric storage contract decimal(18,4); unchanged legacy measurements/notes-only saves retain original value and status/spec metadata. Preserve RowVersion and whole result/evidence set, no clearing completed results, no unsaved visible evidence at submit/review/approve. Investigation states permit pending completion only; prior completed result/resource/LES values are immutable and Released After Investigation remains released absent a new OOS.

Use locked test identity/limits and installed visual/qualitative/numeric policy. Visual Turbidity is AQUASOL AE300 1–25 NTU with no instrument or kit. Structured LES TestIDs2/3 requires verification; conductivity temperature24–26°C representable to2 decimals. Recheck primary/support equipment compatibility, active/qualified/calibration validity and kit expiry against SQL clock. Preserve all existing signed evidence fields, full delta audit, entered-by/time attribution, OOS automatic QE and current closed-disposition gating.

Start: Registered/Incubation -> In Analysis; analysis time >= sampling/receipt and <=SQL now+1minute. Save derives all summary/status from authoritative rows. Submit no pending/QE issue ->Under Review. Review requires independent authorized reviewer ->Reviewed. Approval requires independent QA+CanApproveResults ->Approved and atomic plan sync. CorrectTimes requires CanRegisterSamples, full old six-date snapshot, valid chronology/duration, no locked record/active certificate; AnalysisCompleted is not editable. No Development override is inferred from the service identity.

## Builder-check refinements (authoritative implementation contract)

The fresh builder identified the readonly-principal lock/permission risk. The host executes `Mode=Read` of the same owner procedure, in its existing Serializable transaction, to acquire retained locks and return the canonical ordered snapshot result sets. The client runs the identical query text with SELECT-only hints. `WaterWorkflowSnapshot.FromReader` parses/hashes both identically. Scientific validation uses only these returned authoritative tables, never new unchecked direct UPDATE-lock reads from the readonly service. The canonical query lives in trusted-library `WaterWorkflowSqlContract.SnapshotQuery`; SQL staging composes its escaped owner-lock form into exactly one marker in the reviewed SQL template. C# and PowerShell composition equality is tested.

Canonical snapshot tables/order: Header(Samples plus authoritative point code/type), Results(installed snapshot query columns), Assignments, Resources(latest batch per result), Executions(latest per result), Equipment(all rows for newly selected/support resources), Compatibility, QualityEvents, AffectedResults, Signatures, Certificates, PlanSamples(all linked plans), Plans. Database clock is returned last. Hash clinical tables but exclude clock, full equipment catalog and unrelated plan sample rows; hash stored assignment identity/history and current relevant plan/status/QE/certificate state. Acquire locks on equipment and all related plan rows even when excluded from fingerprint. Actor/version/permissions are locked/validated by owner procedure independently, not part of clinical hash.

Refine CorrectTimes: UI edits SamplingDateTime, ReceivedDateTime, IncubationStartedDateTime, AnalysisStartedDateTime only. IncubationEndDate is a fifth persisted value, derived from the original approved duration under lock; do not make it independently editable. AnalysisCompletedDateTime is read-only comparison evidence.

Plan JSON is server-only Version1, Operation, SampleId, ExpectedStatus, ExpectedSnapshot, Status, AnalysisStartedAt, Times, MarkAnalysisCompleted, Rows[]. Rows carry SampleTestId, WriteResult, invariant ResultValue string/null, Remarks/null, ResultStatus, DeviationType/null, WriteEvidence, EquipmentId/null, SupportingEquipmentIds[], TestKitCode/Lot/Expiry, RawResultSnapshot and optional Execution(ProcedureReference, MethodGuidanceSnapshot, SampleTemperatureC, VerificationReference, VerificationConfirmed, ExecutionRemarks). SQL derives test/equipment identity snapshots, old audit values, database times, summary counts, OOS records and plan synchronization; none are independent remote inputs. Expected ResultRowVersion is recovered from locked authoritative state/plan as needed.

Save Results[] covers exactly the authoritative visible set (installed IsRemovedTest excludes taste/odor variants); hidden rows remain in snapshot and NULL completeness counts. Validator derives original display from the same installed deterministic formatter, never caller IsEdited/original metadata. Display originals remain client validation aids only.

Receipt identity includes original Operation, canonical payload, actor, SID, reason and meaning; excludes fresh ticket, recovery action and current auth-version. Resolve/cancel allow the same currently active authenticated actor/SID after legitimate auth-version changes, while retaining original auth-version as historical evidence. A new write still requires current operation permission and a valid original snapshot. SourceWorkstation is the actual service machine, not an unauthenticated client claim.

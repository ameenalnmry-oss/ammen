# EQ-001 site activity integration

The AMEEN working tree contains equipment activity creation, submission, links, review/approval and printing absent from the qualified PR #62 baseline. Preserve those functions while moving regulated signatures to the existing TLS-pinned local named pipe. The user authorized continuous safe implementation without repeated design approval; no deployment, production activation or merge is authorized before isolated Windows UAT.

Extend the protected transport with a separate activity request rather than reinterpret equipment master actions. Resolve the caller through the existing kernel SID map, exclude the service identity, independently verify the password through the existing service-side AuthService and enforce current stage permissions. The activity SQL adapter must require validated SQL TLS, the configured database, an independent service origin, exact credential rowversion, a unique request ledger and the existing hardened activity procedure in one transaction. It must never insert signature/audit rows directly or mutate existing history.

Rejected approaches: replace the local screen with the older PR screen (loses activity features); retain the HTTP endpoint with desktop-only password checking (does not independently establish the signature credential). The protected activity path is the chosen implementation approach under the user's existing constraints.

Keep old accepted evidence scoped to its tested revision. New behavior requires focused tests, build and Windows SQL/WPF qualification; successful CI does not establish AMEEN site acceptance. Do not weaken the UAT database allowlist or alter existing database names. Do not touch Water workflows.
